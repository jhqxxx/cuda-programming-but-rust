# 编译器优化

cuda-oxide 已经受益于 rustc 和 LLVM 中的优化。`mir-transforms` crate 是
cuda-oxide 在程序仍以 `dialect-mir` 表示时添加自己 pass 的地方。循环展开是
这一层里第一个由 cuda-oxide 自己拥有的优化 pass。

本页先讲面向用户的想法，然后跟踪一个循环走完编译器。阅读它不需要编译器经验。

---

## 什么是 MIR 变换？

rustc 把 Rust 源码下降到 MIR 之后，cuda-oxide 把它导入 `dialect-mir`，在那里
带类型的操作与控制流分支都是显式的。

编译器的这一部分有三项互相关联的工作：

| 工作 | 它做什么 |
|:----|:-------------|
| **分析** | 读取 IR 并记录事实，例如哪些块构成一个循环 |
| **变换** | 在不改变程序计算结果的前提下改写 IR |
| **下降** | 把程序从一种 IR 方言转换成更低层的方言 |

循环分析可以识别出循环的 counter、步长和上限。展开变换利用这些事实改写循环，
使每一趟执行若干个原始迭代。之后的下降把结果转换成 LLVM。

> **注意**
>
> 在本章中，**MIR 变换**指的是对 cuda-oxide 导入的 `dialect-mir` 做变换。
> 它们不直接修改 rustc 内部的 MIR。

---

## 变换在哪里运行

优化层位于设备编译流水线的中段：

```text
Rust 源码
    → rustc MIR
    → mir-importer
    → dialect-mir
    → mem2reg
    → mir-transforms       ← cuda-oxide 优化
    → mir-lower
    → LLVM 方言
    → LLVM IR
    → PTX
```

[MIR importer](mir-importer.md)最初用 load 和 store 表示局部变量。`mem2reg`
把合格的 local 提升为 **SSA 值**，此时每个值只有一个定义，块参数在块之间
传递值。这让循环计数器及其更新变得足够显式，优化 pass 才能对它们做推理。

变换在这里运行，是因为 `dialect-mir` 保留了 Rust 层面的类型与操作，让
cuda-oxide 有针对性的改写更容易表达。随后[下降流水线](lowering-pipeline.md)
把优化后的结果转换掉。

完整的变量调试构建会跳过 `mem2reg` 和循环展开。把源码变量留在稳定的内存
位置上，能给 cuda-gdb 更好的调试体验。

## 诊断仍留在栈上的 local

优化过的 verbose 构建还会检查将要传给 `llc` 的那个确切的 LLVM IR。如果某个
Rust local 的栈分配在 cuda-oxide 的 `mem2reg` 和 LLVM 的 `-O2` 标量替换流水线
之后都活了下来，cuda-oxide 会在生成 PTX 之前报告它。例如：

```text
warning: `kernel` 中的 local `scratch`（`[u32; 4]`，16 字节）无法提升到寄存器
  = note: 被一个非常量值索引；该分配在 LLVM 标量替换之后仍然存在，保留在栈上
  = help: 当索引范围有界时，改用常量索引或一个小型的 match/select
```

动态索引是常见的阻碍之一，因为当被选中的元素未知时，LLVM 无法用彼此独立的
SSA 值替换一个小聚合。把一个地址传给另一个函数、把它存成指针、把它返回，或
以其它方式让它可被观察到，同样可能阻止提升。当存活下来的使用模式不属于
cuda-oxide 识别的那些保守情况之一时，告警仍然会指出是哪个 local，但给出的
是通用的标量替换解释，而不是去猜测原因。

这个检查只在 LLVM 优化 pass 成功之后运行，并且只在 verbose 模式下运行：

```bash
cargo oxide build <example> --verbose
```

这个放置位置很重要。如果在 cuda-oxide 的 `mem2reg` 之后立刻报告，会对那些
LLVM SROA 之后才移除的分配产生误报。对不做优化的构建和完整变量调试构建会
跳过该检查，因为这些模式有意保留优化构建通常会尝试提升的存储。

## 第一个 pass：循环展开

循环通常每执行一次迭代就测试一次条件并跳回去。**展开**会复制循环体，使得在
新循环里走一趟就完成若干次迭代的工作。

考虑 kernel 或设备函数里这个小巧的计数循环：

```rust
let mut i = 0u32;
#[unroll]
while i < 4 {
    work(i);
    i += 1;
}
```

概念上，完全展开把它变成：

```rust
work(0);
work(1);
work(2);
work(3);
```

指向循环头的条件与回跳都消失了。更重要的是，每个副本里的 `i` 现在都是常量值，
从而暴露出进一步的简化机会。

代价是生成的代码更大。更大的循环体也可能需要更多寄存器，所以展开是对编译器的
一个请求，而不是性能更好的承诺。

---

## 完全展开与部分展开

cuda-oxide 提供两种形式：

| 注解 | 何时使用 | pass 产出什么 |
|:-----------|:------------|:------------------------|
| `#[unroll]` | trip count 在编译期已知 | 每次迭代一份循环体副本；循环消失 |
| `#[unroll(N)]` | trip count 可能只在运行时才知道 | 主循环里 `N` 份副本，外加一个剩余循环 |

### 完全展开

裸的 `#[unroll]` 需要编译期已知的 trip count：

```rust
let mut i = 0u32;
#[unroll]
while i < 8 {
    sum += i;
    i += 1;
}
```

pass 会给这八份副本分别赋予 `0` 到 `7` 的计数器值。常量传播随后可以折叠由
这些字面量派生出的表达式。

### 部分展开

当上限是运行时值时，`#[unroll(4)]` 也能工作：

```rust
let mut i = 0u32;
#[unroll(4)]
while i < n {
    process(i);
    i += 1;
}
```

如果 `n` 是 `10`，主循环处理两组、每组四个迭代。剩余循环处理迭代 `8` 和 `9`。
当 `n` 不能被四整除时，结果依然正确。

这消掉了主循环每四次测试中的三次，并给编译器一片更大的直线型区域去优化。

## 一个有用的窥孔优化：折叠流水线阶段

部分展开有一个小麻烦：主循环仍然带着一个运行时计数器。cuda-oxide 为一种常见
的软件流水线模式内置了一个小的**窥孔优化**：

```rust
let mut k_idx = 0u32;
#[unroll(4)]
while k_idx < k_iters {
    let stage = k_idx & 3;
    match stage {
        0 => consume_stage_0(),
        1 => consume_stage_1(),
        2 => consume_stage_2(),
        3 => consume_stage_3(),
        _ => {}
    }
    k_idx += 1;
}
```

展开后的主循环计数器每次前进四。于是它的低两位在组与组之间不变，所以四份
副本的 stage 值是固定的：

```text
copy 0: (k_idx + 0) & 3  →  0
copy 1: (k_idx + 1) & 3  →  1
copy 2: (k_idx + 2) & 3  →  2
copy 3: (k_idx + 3) & 3  →  3
```

窥孔优化把这些表达式替换成字面量。常量传播随后移掉死掉的 `match` 分支，
留下四段直线型、按 stage 特化的循环体。剩余循环保持完整，用于处理剩下的迭代。

当 `k_idx` 是无符号数时，`k_idx % 4` 同样有效，`(k_idx + 1) & 3` 这样的常量
偏移也能被识别。只有当这些形式的二的幂周期能整除展开步长时，pass 才会折叠
它们。

### 为什么运行时基数无法折叠

表达式必须直接基于循环计数器：

```rust
let stage = k_idx & 3;                    // 可以折叠

let global_k = tile_k_base + k_idx;
let stage = global_k & 3;                 // tile_k_base 是运行时值：无法折叠
```

因为运行时的 `tile_k_base` 的低位在编译期未知，编译器无法为每份副本挑选一个
字面量 stage。只有当算法另外保证了 `tile_k_base` 是四的倍数时，把它改写成前
一种形式才是正确的。pass 刻意拒绝去猜。

> **注意**
>
> 完全展开不需要这个窥孔优化。完全展开后的计数器在每份副本里本来就是字面量，
> 所以普通的常量传播就能完成这项工作。

## 注解如何抵达 pass

源码属性经由六个阶段穿过编译器：

1. `#[kernel]` 或 `#[device]` 宏消费 `#[unroll]` 或 `#[unroll(N)]`，并在那个
   循环的开头插入一个内部标记调用。
2. `mir-importer` 识别这个调用，并发出一条 `mir.unroll_hint` 操作。该标记
   不产生任何运行时代码。
3. `LoopInfo` 找到所在的循环，同时归纳分析找出它的 counter、起始值、步长、
   上限，以及（在可能时）trip count。
4. pass 规范化受支持的控制流。它把多条 `continue` 路径合并成一条回到循环头的
   路径，并把受支持的循环携带值从完全展开的循环中引出。
5. 变换为完全展开或部分展开克隆循环体并重新接线。
6. 清理阶段折叠常量、简化分支，并移除死代码或不可达代码。

展开 pass 会原样放过没有展开提示的函数。如果它无法证明所请求的改写是安全的，
它会打印一条告警并且不施加展开；循环以相同的行为继续。

## 受支持的循环与安全回退

当前的 pass 有意只识别一组保守的循环形状：

两种形式都需要一个 pass 能跟踪的计数器：编译期常量的起始值、每条回到循环头的
路径上相同的固定步长，以及一个直接拿计数器与上限比较的简单、无副作用的测试。
该循环还必须在其循环头之前有一个普通入口。对于不寻常或不可归约的控制流，
编译器会告警并且不展开该循环。

| 形状 | 当前行为 |
|:------|:-----------------|
| 显式的计数 `while` 循环 | 满足上述要求时受支持 |
| 基于范围的 `for` 循环 | 尚未识别 |
| 编译期常量 trip count + `#[unroll]` | 完全展开 |
| 运行时、循环不变的上限 + `#[unroll(N)]` | 部分展开 |
| 多条 `continue` 路径但计数器步长相同 | 合并后展开 |
| 提前 `break` 或多个出口 + `#[unroll]` | 受支持 |
| 提前 `break` 或另一个出口 + `#[unroll(N)]` | 告警；跳过部分展开 |
| 嵌套循环 | 只展开带注解的那个循环 |

部分展开还要求 `N >= 2`、正的计数器步长、`<` 或 `<=` 比较，以及一个在循环
内部不会改变的循环上限。

当带注解的外层循环里含有未注解的内层循环时，每份外层副本都会得到那个内层循环
的完整克隆；内层循环仍然是个循环。当两个循环都带注解时，编译器先处理内层循环。

为了限制编译时间与内存，一个注解最多可以创建 1,024 份循环体副本、8,192 个
克隆的基本块，以及 65,536 个克隆的操作。超过其中任一限制的请求会告警并且
不被展开。

完整的 kernel 作者参考见[循环展开](../gpu-programming/kernels-and-device-functions.md#loop-unrolling)。

## 你应该在什么时候展开？

好的候选是：

- 具有固定 trip count 的小循环；
- 分支开销要紧的热点计数循环；
- 展开之后 stage 选择变成常量的软件流水线；
- 若干份独立副本能暴露指令级并行性的循环。

当循环体很大，或者已经用了很多寄存器时要谨慎。额外的代码可能增加寄存器压力、
降低占用率，或者给指令缓存施加更大压力。

选择与算法结构匹配的因子 —— 通常是流水线深度或另一个小的自然分组 —— 并对
结果做基准测试。去掉 `#[unroll]` 应该永远是一个容易做的对比。

要检查这个 pass 的分析，用 verbose 构建：

```bash
cargo oxide build <example> --verbose
```

verbose 模式会打印所请求的因子以及 pass 找到的循环事实。如果某个请求被跳过，
告警会解释原因。循环编号与分析字段属于内部细节，可能会变化。

## 未来变换的家

`mir-transforms` crate 把可复用的分析与 IR 变更分开存放：

```text
cuda-oxide/crates/mir-transforms/src/
├── analyses/
│   ├── loop_info.rs      # 哪些块属于每个循环？
│   └── induction.rs      # counter、步长、上限与 trip count 分别是什么？
├── canonicalize.rs       # 把受支持的控制流整理成更简单的形状
└── unroll.rs             # 证明、克隆、重新接线并清理循环
```

这种分离为未来的优化提供了一个可预期的落脚点：分析收集事实，规范化把等价的
形状整理一致，变换执行保持行为的改写。`mir-importer/src/pipeline.rs` 控制每个
pass 何时运行。

每个变换都应遵循与展开器相同的规则：证明改写是安全的、为资源使用设界，并且
当程序落在受支持形状之外时，在不改变行为的前提下回退。

聚焦的测试套件用以下命令运行：

```bash
cargo test -p mir-transforms --all-targets
```

从这里开始，[下降流水线](lowering-pipeline.md)会解释优化后的 `dialect-mir`
如何变成 LLVM 方言，并最终变成 PTX。
