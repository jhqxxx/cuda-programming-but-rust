# 目录生成的内联函数

大多数 cuda-oxide 设备内联函数并不是通过独立地编辑编译器各阶段来实现的。它们
被描述为经过评审的目录输入，而 `cuda-intrinsics-gen` 会从该契约生成重复性的
API、方言、导入器、下降、目标、参考和探测表面。

当内联函数符合生成的目录模型时，请使用此工作流。对于需要定制校验或下降、目录
无法表达的操作，请改用 [添加新的内联函数](adding-new-intrinsics.md)。

---

## 首先选择正确的路径

在编辑任何东西之前，先找到语义和下降形状最接近的现有内联函数。

```text
Does an existing catalog family model the intrinsic?
    |
    +-- yes -> extend that overlay family and the ABI ledger
    |
    +-- no  -> determine whether the generator needs a new family/shape
               or whether the operation is genuinely hand-written
```

仅有一条 LLVM 声明还不足以纳入一个内联函数。目录还记录 cuda-oxide 策略，例如
其 Rust API、安全性与效果、预期的 PTX 形式、目标要求、ABI 身份以及下降证据。

因此，正常的贡献路径是扩展一个现有的、经过评审的族，而不是直接编辑生成的 Rust
文件或 `intrinsics/catalog.json`。

---

## 真相之源

生成的内联函数流水线由经过评审的输入组装，并解析为一个生成的目录：

```text
intrinsics/upstream.lock -> intrinsics/imported.json ----\
intrinsics/overlay.toml -> intrinsics/overlay/*.toml -----+
intrinsics/abi-v1.toml -----------------------------------+--> resolve
intrinsics/evidence/*.json -------------------------------/       |
                                                                  v
                                                     intrinsics/catalog.json
                                                            GENERATED
                                                                  |
                                                                  v
                                                        generated outputs
```

它们的角色各不相同：

| 文件 / 产物 | 角色 |
| :-------------- | :--- |
| `intrinsics/upstream.lock` | 锁定被导入事实所使用的 LLVM 源码/提取身份，以及证据探测必须在其下运行的 rustc 提交。 |
| `intrinsics/imported.json` | 记录被锁定的 LLVM/NVPTX 源码声明了什么。普通的内联函数新增使用这个已提交的文件；它们不会重新运行提取。 |
| `intrinsics/overlay.toml` | 显式索引已纳入的 overlay 分片。 |
| `intrinsics/overlay/*.toml` | 记录经过评审的内联函数族的 cuda-oxide 策略。 |
| `intrinsics/abi-v1.toml` | 只增不改的稳定内联函数 ABI 台账。 |
| `intrinsics/evidence/*.json` | 在路径要求时记录经过评审的下降证据。 |
| `intrinsics/catalog.json` | 解析后的生成计划。不要手工编辑它。 |

生成的源码以及探测/参考输出都带有 `DO NOT EDIT` 标记。请修改它们的源输入并
重新生成。

### 目录元数据

overlay 清单携带解析后目录的版本和后端元数据。这些值描述的是目录契约；它们
不是按内联函数的旋钮。

这里涉及两个不同的 `schema` 数字，生成器每一侧各一个：

```text
intrinsics/overlay.toml   schema = 44   (overlay input format)
        | cuda-intrinsics-gen
        v
intrinsics/catalog.json   "schema": 46  (serialized catalog format)
```

- `schema`（位于 `overlay.toml` 中）标识生成器所接受的 overlay **输入**格式
  （`cuda-oxide/crates/cuda-intrinsics-gen/src/resolve/overlay.rs` 中的
  `OVERLAY_SCHEMA`）；解析器会拒绝不匹配的清单。它不是目录格式版本。
- `catalog_version` 标识经过评审的目录契约。
- `intrinsic_abi` 标识其稳定条目记录在 `intrinsics/abi-v1.toml` 中的内联函数
  ABI 世代。
- `backend_profile` 选择在解析下降证据时使用的、经过评审的后端配置文件。

贡献者通常只会在有意的目录、ABI 或后端配置文件转换时更改这些值。不要在生成的
`intrinsics/catalog.json` 中直接合成或编辑相应的元数据。

### catalog.json 头部字段

生成的目录在解析时会给自己的头部盖章。作为参考，由于该文件是生成的且除此之外
没有文档：

- `schema`：**序列化目录**格式的版本（同一个 `resolve/overlay.rs` 中的
  `CATALOG_SCHEMA`）。与 overlay 的 `schema` 不同；见上面的示意图。
- `catalog_version`：经过评审的目录契约，从 `overlay.toml` 复制而来。
- `intrinsic_abi`：ABI 世代，从 `overlay.toml` 复制而来；其稳定条目位于
  `intrinsics/abi-v1.toml` 中。
- `generator_version`：产生该目录的 `cuda-intrinsics-gen` crate 版本（其
  Cargo 包版本）。同一个值出现在每个生成文件的
  `@generated by cuda-intrinsics-gen <version>` 横幅中。

## 正常工作流：扩展现有的族

### 1. 找到最近的同类项

从 `intrinsics/overlay/` 开始，而不是从生成的 Rust 代码开始，也不是去滚动
`intrinsics/imported.json`。

找一个具有相同族和下降形状的现有条目，然后只在必须与上游一致的字段上使用导入
的 LLVM 事实。

例如：

```bash
grep -R 'id = "<nearest-sibling>"' intrinsics/overlay
rg '<llvm-or-record-name>' intrinsics/imported.json
```

优先复制一个经过验证的同类项，而不是从零构造条目。解析器刻意采用 fail-closed
策略，但匹配既定的族形状能让评审规模更小，也更容易发现意外的生成差异。

### 2. 添加或扩展 overlay 条目

编辑以下路径下的相应文件：

```text
intrinsics/overlay/<family>.toml
```

overlay 是手工编辑的策略输入。不要编辑
`cuda-oxide/crates/dialect-nvvm/src/ops/generated/` 下对应的操作、生成的导入器
分发、生成的下降表，或 `intrinsics/catalog.json`。

如果这次贡献需要一个**新的 overlay 分片**，还要把该分片加入以下文件中已排序的
`shards` 列表：

```text
intrinsics/overlay.toml
```

`generate` 和 `check` 会把索引与 overlay 目录对齐，并拒绝未加索引的分片。

### 3. 追加 ABI 台账条目

在以下文件的末尾添加新的稳定身份：

```text
intrinsics/abi-v1.toml
```

该台账是只增不改的。现有条目不得被重排、删除、重新编号或改作他用。目录身份、
操作键和原始 Rust 签名必须与 overlay 条目一致。

把 ABI ID 当作合并时的资源。如果另一个内联函数 PR 先落地，请变基到最新的
`main`，在新台账尾部之后追加，并重新生成。不要仅仅因为分支早些时候用过某个
数字区间就保留一个已作废的区间。

### 4. 仅在需要时处理下降证据

如果新内联函数使用已经评审过的下降/证据形状，请遵循现有的同类项契约。普通的
目录新增并不一定需要新的证据文件。

如果后端路径是新的且需要候选证据，请使用显式的候选探测：

```bash
HOST="$(rustc -vV | sed -n 's/^host: //p')"
LLC="$(rustc --print sysroot)/lib/rustlib/$HOST/bin/llc"

cargo run -p cuda-intrinsics-gen -- probe --candidate \
  --intrinsic <catalog-id> \
  --llc "$LLC" \
  --gpu-target <sm-target> \
  --ptx-feature <ptx-feature> \
  --ptxas <path-to-ptxas>
```

在终端汇编被刻意设为不可用的系统上，把 `--ptxas <path-to-ptxas>` 替换为显式的
`--skip-terminal` 标志。候选模式要求两者之一；它不会静默回退。

在把任何证据提升为已提交契之前，请先审查候选输出。

### 5. 重新生成

运行：

```bash
cargo run -p cuda-intrinsics-gen -- generate
```

然后在运行更广泛的检查之前，检查工作树和 diff：

```bash
git status --short
git diff --stat
git diff -- intrinsics cuda-oxide/crates/cuda-intrinsics cuda-oxide/crates/cuda-device \
  cuda-oxide/crates/dialect-nvvm cuda-oxide/crates/mir-importer cuda-oxide/crates/mir-lower \
  cuda-oxide/crates/cuda-oxide-codegen cuda-oxide/crates/rustc-codegen-cuda
```

也检查一下 `git status --short`：新建的 overlay 或证据文件在被暂存之前是未跟踪
的，因此不会出现在 `git diff` 中。

对于符合现有族的新增，生成的变更应当遵循同类项的模式。意外的无关变更就是停
下来重新检查 overlay、台账、证据或分支基线的理由。

## 推送前验证

仓库为生成的内联函数 CI 契约提供了一个本地入口点：

```bash
just -f cuda-oxide/Justfile check-intrinsics upstream/main
```

如果实际的 PR 基线不是 `upstream/main`，请使用实际基线。

该 recipe 镜像了生成的内联函数 CI 任务，目前覆盖三项承重检查：

```text
cuda-intrinsics-gen check
cuda-intrinsics-gen probe --all --skip-terminal --per-target
cuda-intrinsics-gen check-abi-history --base-ref <base>
```

请使用 `just -f cuda-oxide/Justfile check-intrinsics ...` 作为正常的贡献者接口，
而不是把底层命令复制进脚本。当 CI 契约获得额外覆盖时，该 recipe 可以演进。

这些门禁自带两项环境要求：

- `check-abi-history` 会沿 git 历史回溯到基线引用，因此需要完整克隆。CI 以
  `fetch-depth: 0` 检出；浅层本地克隆可能无法解析基线。
- 生成器在写出生成源码时会外调 `rustfmt`。这就是 `rust-toolchain.toml` 锁定
  `rustfmt` 组件的原因；在正常检出上不需要额外安装。

在开发单个内联函数时，为了进行聚焦探测，你也可以运行：

```bash
cargo run -p cuda-intrinsics-gen -- probe \
  --intrinsic <catalog-id> \
  --skip-terminal
```

最后，运行你所改动文件所需的正常检查。对于同时更新本书的改动：

```bash
just -f cuda-oxide/Justfile book
bash cuda-oxide/scripts/check-book-api-names.sh
git diff --check
```

## 当现有目录无法表达它时

缺少同类项是一个设计信号。如果该内联函数需要生成器未建模的下降形状、操作数
适配器、结果契约或族结构，那么这次改动就不再是一次小小的目录纳入。

新的生成形状通常涉及生成器代码，例如：

```text
cuda-oxide/crates/cuda-intrinsics-gen/src/model/
cuda-oxide/crates/cuda-intrinsics-gen/src/resolve/
cuda-oxide/crates/cuda-intrinsics-gen/src/render/
```

并且可能还需要 `cuda-oxide/crates/mir-lower/` 或
`cuda-oxide/crates/dialect-nvvm/` 下真正的编译器下降改动。

尽可能把这类工作与例行的目录纳入分开。ABI 台账和生成的内联函数验证契约仍然
适用。

如果该操作按设计需要定制校验或下降、且应当留在目录之外，请遵循
[添加新的内联函数](adding-new-intrinsics.md) 中的手写工作流。

---

## 提取不属于正常新增的一部分

`extract` 命令会刷新导入的 LLVM 事实。它用于 LLVM 源码或锁定版本的更新，而不是
用于添加一个已经存在于已提交 `intrinsics/imported.json` 中的内联函数。

正常新增使用已提交的导入事实。这使例行的内联函数工作独立于 LLVM 检出，并让
经过评审的 overlay、ABI 台账和证据成为显式的 cuda-oxide 策略层。

---

## 不要手工编辑什么

对于目录生成的内联函数，不要直接编辑：

- `intrinsics/catalog.json`；
- `cuda-oxide/crates/cuda-intrinsics/src/generated/` 下的生成文件；
- `cuda-oxide/crates/cuda-device/src/generated/` 下的生成文件；
- `cuda-oxide/crates/dialect-nvvm/src/ops/generated/` 下的生成文件；
- `mir-importer` 中生成的内联函数分发；
- `mir-lower` 中生成的内联函数转换表；
- 生成的目标/收集器元数据；
- 生成的探测/参考输出。

如果重新生成覆盖了某次手工编辑，那么这次编辑做在了错误的层。真相之源是拥有
该输出的、经过评审的目录输入、ABI、证据或生成器逻辑。
