# 添加新的内联函数

cuda-oxide 有两条内联函数贡献路径。大多数设备内联函数是**目录生成**的：贡献者
编辑经过评审的目录输入，并让 `cuda-intrinsics-gen` 一起产生 API、方言、导入器、
下降、目标、参考和探测表面。目录无法表达的、带定制校验或下降的操作则保持手写。

除非你已经确认现有目录模型无法表示该操作，否则请从
[目录生成的内联函数](catalog-generated-intrinsics.md) 开始。本章记录编译器各阶段
以及手写路径，并用生成的内联函数作为流经这些阶段的表示形式的具体示例。

---

## 五阶段流水线

每个 GPU 内联函数都走通过编译器的同一条路径：

```text
cuda-device          User writes:  thread::threadIdx_x()
    │
    ▼
mir-importer       Compiler sees the call, emits a `dialect-nvvm` op
    │
    ▼
dialect-nvvm       The op lives here as a verified IR node
    │
    ▼
mir-lower          Converts the `dialect-nvvm` op into an LLVM dialect op
    │
    ▼
llvm-export        Exports textual LLVM IR  →  llc turns it into PTX
```

在 `mir-lower` 阶段你要在两种策略中选择一种：

| 策略             | 何时使用                                                                     | 示例                                   |
| :--------------- | :--------------------------------------------------------------------------- | :------------------------------------- |
| LLVM 内联函数调用 | LLVM 已经有内建的对应物                                                      | `threadIdx_x`、warp shuffle、屏障      |
| 内联 PTX 汇编     | 不存在 LLVM 内联函数，或者你需要对 PTX 指令进行精确控制                       | `trap`、`wgmma`、`tcgen05`、`mbarrier` |

两种策略都在下文演示。

---

## 示例 1：`threadIdx_x`（简单情形）

`threadIdx_x()` 是 GPU 内联函数里的"Hello, World"：零参数，一个 `u32` 结果，
直接映射到单个 LLVM NVVM 内联函数。如果你能看懂这个例子，你就能添加任何简单的
内联函数。

### 第 1 阶段 —— 在 `cuda-device` 中声明

**文件：** `cuda-oxide/crates/cuda-device/src/thread.rs`

```rust
#[inline(never)]
pub fn threadIdx_x() -> u32 {
    unreachable!("threadIdx_x called outside CUDA kernel context")
}
```

在理解这个技巧之前，有两条规则可能看起来奇怪：

- **`#[inline(never)]`** 让该函数在 MIR 中保持为一个可辨识的调用。如果 rustc
  把它内联了，编译器看到的就会是 `unreachable!()`，而不是一个它能够拦截的调用。
  那将会……不太有帮助。

- **函数体是 `unreachable!()`**，因为这个函数实际上从不运行。编译器在任何 GPU
  代码执行之前就把整个调用替换为一个 `dialect-nvvm` 操作。把这个函数看作一个
  占位符 —— 一张写着"亲爱的编译器，请在此处插入一条 GPU 指令"的便条。

> **提示**
>
> 在函数上方用注释记录该内联函数映射到的 LLVM IR 或 PTX。未来的你（或未来的
> 贡献者）会感谢现在的你。

### 第 2 阶段 —— 定义 `dialect-nvvm` 操作

**文件：** `cuda-oxide/crates/dialect-nvvm/src/ops/` 中某个手写操作模块 ——
`asm.rs`、`atomic.rs`、`cluster.rs`、`debug.rs`、`grid.rs`、`memory.rs` 或
`wgmma.rs`。

> **重要**
>
> `dialect-nvvm` 中有两类操作，其中只有一类是手写的。
>
> 任何由 `intrinsics/catalog.json` 描述的内容都由 `cuda-intrinsics-gen`
> **生成**到 `cuda-oxide/crates/dialect-nvvm/src/ops/generated/` 中，那里的每个
> 文件都以 `// @generated by cuda-intrinsics-gen ... DO NOT EDIT.` 开头。紧接
> 下文用作示例的操作就是其中之一：`tid.x` 是一个目录内联函数，其操作今天位于
> `ops/generated/sreg.rs` 中。在那里手工添加一个操作会被下一次生成器运行撤销。
>
> 关于拥有那些生成文件的贡献者工作流，包括 overlay、只增不改的 ABI 台账、
> 重新生成、证据以及本地 CI 门禁，见
> [目录生成的内联函数](catalog-generated-intrinsics.md)。
>
> 上面提到的模块是手写的那些 —— 目录未描述的、带定制校验或下降的操作。本节中
> 的代码展示了操作无论哪种方式呈现的形状；只有对第二类才需要你自己编写。

```rust
#[pliron_op(name = "nvvm.read_ptx_sreg_tid_x", dialect = "nvvm", format)]
pub struct ReadPtxSregTidXOp;

impl Verify for ReadPtxSregTidXOp {
    fn verify(&self, ctx: &Context) -> Result<(), Error> {
        let op = &*self.get_operation().deref(ctx);
        if op.get_num_operands() != 0 {
            return verify_err!(op.loc(), "expected 0 operands");
        }
        if op.get_num_results() != 1 {
            return verify_err!(op.loc(), "expected 1 result");
        }
        Ok(())
    }
}
```

然后注册它，让 pliron 知道该操作存在：

```rust
pub(super) fn register(ctx: &mut Context) {
    ReadPtxSregTidXOp::register(ctx, ReadPtxSregTidXOp::parser_fn);
}
```

`Verify` trait 会及早捕获结构性 bug。如果有东西意外地用两个操作数创建这个操作，
校验会以清晰的消息失败，而不是在三个阶段之后产生垃圾 PTX。

### 第 3 阶段 —— 在 `mir-importer` 中识别

**文件：** `cuda-oxide/crates/mir-importer/src/translator/terminator/intrinsics/generated/`
下该内联函数所属的族模块

当翻译器处理 MIR 时，每次函数调用都会经过 `terminator/mod.rs` 中的
`try_dispatch_intrinsic()`。被调用者的完全限定域名（FQDN）通过
`extract_func_info()` 从 `CrateDef::name()` 得到，产生像
`cuda_device::thread::threadIdx_x` 这样的路径。对于像 `tid.x` 这样的目录内联
函数，`try_dispatch_intrinsic()` 会交给生成的调度器，后者的 match 分支检查 FQDN：

```rust
"cuda_intrinsics::__cuda_oxide_intrinsic_abi_v1::i0001"
| "cuda_device::thread::threadIdx_x"
| "cuda_device::threadIdx_x" => {
    require_arity(name, args.len(), 0, &loc)?;
    Ok(Some(helpers::emit_generated_nvvm_intrinsic(
        ctx,
        body,
        ReadPtxSregTidXOp::get_concrete_op_info(),
        "v1:i0001",
        destination, target, block_ptr, prev_op,
        value_map, block_map, loc,
    )?))
}
```

该分支匹配完整模块路径（`cuda_device::thread::threadIdx_x`）、重导出的名称
（`cuda_device::threadIdx_x`）以及一个带版本的 ABI 别名，因此无论用户如何导入
该函数，调用都会被拦截。FQDN 按原样用于匹配 —— 在内联函数检查之前不会发生
`::` 到 `__` 的转换。

`emit_generated_nvvm_intrinsic()` 辅助函数适用于*任何*零参数、单结果的 NVVM
内联函数。它在插入 NVVM 操作之前准备好 MIR 目标，用其目录 ABI 标记给该操作
打上标签，通过那个准备好的目标写入结果，并发出到下一个基本块的分支。你永远
不需要自己编写这个分支：一旦经过评审的 overlay、ABI 和证据输入解析为
`intrinsics/catalog.json`，`cuda-intrinsics-gen` 就会发出它。`terminator/mod.rs`
中的手写分支只为目录无法描述的内容而存在。

### 第 4 阶段 —— 下降为 LLVM 方言

**文件：** `cuda-oxide/crates/mir-lower/src/convert/generated_intrinsics/` 下该内联
函数所属的族模块

该操作实现 `MirToLlvmConversion` op 接口。对于目录内联函数，这个实现会与一个
共享转换器一起生成：

```rust
#[op_interface_impl]
impl MirToLlvmConversion for ReadPtxSregTidXOp {
    fn convert(
        &self,
        ctx: &mut Context,
        rewriter: &mut DialectConversionRewriter,
        _operands_info: &OperandsInfo,
    ) -> Result<()> {
        convert_zero_operand_scalar_direct(
            ctx,
            rewriter,
            self.get_operation(),
            32,
            "llvm_nvvm_read_ptx_sreg_tid_x",
        )
    }
}
```

共享转换器发出 LLVM 内联函数调用：

```rust
fn convert_zero_operand_scalar_direct(
    ctx: &mut Context,
    rewriter: &mut DialectConversionRewriter,
    op: Ptr<Operation>,
    width: u32,
    intrinsic_name: &str,
) -> Result<()> {
    let result_ty = IntegerType::get(ctx, width, Signedness::Signless);
    let function_ty = llvm_types::FuncType::get(ctx, result_ty.into(), vec![], false);
    let call = call_intrinsic(ctx, rewriter, op, intrinsic_name, function_ty, vec![])?;
    rewriter.replace_operation(ctx, op, call);
    Ok(())
}
```

非目录操作的手写转换遵循 `convert/interface_impls.rs` 中的相同模式，委托到
`convert/intrinsics/` 各模块中。

> **注意**
>
> LLVM 内联函数名使用点号（`llvm.nvvm.read.ptx.sreg.tid.x`），但 pliron 标识符
> 不能包含点号。内部我们使用下划线（`llvm_nvvm_read_ptx_sreg_tid_x`）。导出
> 阶段再把它们转换回来。

### 第 5 阶段 —— 导出（无需改动）

**文件：** `cuda-oxide/crates/llvm-export/src/export/`（导出模块）

`CallOp` 导出器已经处理了下划线到点号的转换：

```rust
let fixed_name = if name.starts_with("llvm_nvvm") {
    name.replace('_', ".")
} else {
    strip_device_prefix(&name)
};
```

由于 `threadIdx_x` *不是* convergent（它是一次每线程的寄存器读取，而不是集合
操作），不需要向 `is_convergent_intrinsic()` 添加任何内容。

**最终输出：**

```llvm
declare i32 @llvm.nvvm.read.ptx.sreg.tid.x()
%v5 = call i32 @llvm.nvvm.read.ptx.sreg.tid.x()
```

经过 `llc` 之后：

```text
mov.u32  %r1, %tid.x;
```

五个阶段，一条 PTX 指令。还不错。

## 示例 2：`shuffle_xor`（复杂情形）

Warp shuffle 更有意思。用户的简写传入两个参数，但底层的 LLVM 内联函数期待*四*
个。多出来的一个（成员掩码）在源码层面填入，另一个（clamp）由下降阶段填入。
该操作还是 **convergent** 的，意味着 LLVM 不得跨控制流移动、复制或推测执行它。

### 第 1 阶段 —— 在 `cuda-device` 中声明

**文件：** `cuda-oxide/crates/cuda-device/src/warp.rs`

```rust
#[inline(never)]
pub fn shuffle_xor_sync(mask: u32, var: u32, lane_mask: u32) -> u32 {
    let _ = (mask, var, lane_mask);
    unreachable!("shuffle_xor_sync called outside CUDA kernel context")
}

#[inline(always)]
pub fn shuffle_xor(var: u32, lane_mask: u32) -> u32 {
    shuffle_xor_sync(u32::MAX, var, lane_mask)
}
```

内联函数桩是带掩码的 `_sync` 形式，与之前相同的模式；`let _ = (mask, var,
lane_mask);` 抑制未使用变量警告 —— 一个小小的人情，没有代价。裸的
`shuffle_xor` 简写完全不是桩：它是一个 `#[inline(always)]` 包装器，提供完整
warp 掩码（`u32::MAX`）并调用那个桩。编译器只会匹配 `_sync` 这个名字；包装器
是普通的 Rust 代码。

### 第 2 阶段 —— 定义 `dialect-nvvm` 操作

**文件：** `cuda-oxide/crates/dialect-nvvm/src/ops/generated/warp_shuffle.rs`。
warp shuffle 和 `tid.x` 一样是目录内联函数，所以这个操作是生成的而不是手打
出来的；以下是真实定义的精简版：

```rust
/// 与指定的 XOR 伙伴 lane 交换一个 32 位值。
///
/// 操作数为 `[member_mask, value, lane_or_delta]`。
/// 生成的下降会插入所选 shuffle 模式所需的固定 clamp。
#[pliron_op(
    name = "nvvm.shfl_sync_bfly_i32",
    format,
    interfaces = [NOpdsInterface<3>, NResultsInterface<1>],
)]
pub struct ShflSyncBflyI32Op;

impl Verify for ShflSyncBflyI32Op {
    fn verify(&self, ctx: &Context) -> Result<(), Error> {
        let op = self.get_operation().deref(ctx);
        if op.get_num_operands() != 3 || op.get_num_results() != 1 {
            return verify_err!(
                op.loc(),
                "nvvm.shfl_sync_bfly_i32 requires exactly [member_mask, value, lane_or_delta] and one result"
            );
        }
        // ... 对全部三个操作数和结果做 i32 类型检查 ...
        Ok(())
    }
}
```

这次是三个操作数（成员掩码、值、lane 掩码），一个结果。

### 第 3 阶段 —— 在 `mir-importer` 中识别

**文件：** `cuda-oxide/crates/mir-importer/src/translator/terminator/intrinsics/generated/`
下该内联函数所属的族模块

> **重要**
>
> warp shuffle 是目录内联函数，所以它们的分发分支*以及*它们的参数翻译发射器
> 都被生成到 `generated/warp_shuffle.rs` 中，紧挨着第 2 阶段的操作。关于
> shuffle 的任何内容都不是手写的。手写分发位于 `terminator/mod.rs` 中的
> `try_dispatch_intrinsic()`，覆盖目录无法描述的内容。例如，
> `core::intrinsics::typed_swap_nonoverlapping`（`core::mem::swap` 背后的原语）
> 就在那里被匹配，并由同文件中的手写 `emit_typed_swap()` 下降为两个不重叠
> 指针上的 load/load/store/store 交叉交换。这是任何目录条目都无法表达的。

带参数的内联函数会先翻译用户的每个操作数，然后再构建操作。以下是
`shuffle_xor_sync` 的生成分支，已精简：

```rust
"cuda_device::warp::shuffle_xor_sync" => {
    require_arity(name, args.len(), 3, &loc)?;
    let (member_mask, last_op) =
        rvalue::translate_operand(ctx, body, &args[0], /* ... */)?;
    let (value, last_op) =
        rvalue::translate_operand(ctx, body, &args[1], /* ... */)?;
    let (lane_or_delta, last_op) =
        rvalue::translate_operand(ctx, body, &args[2], /* ... */)?;
    let shuffle = ShflSyncBflyI32Op::build(ctx, member_mask, value, lane_or_delta);
    shuffle.deref_mut(ctx).set_loc(loc.clone());
    helpers::set_generated_intrinsic_marker(ctx, shuffle, "v1:i0051");
    let (prepared_destination, prepared_last_op) = helpers::prepare_destination_write(
        ctx, body, destination, value_map, block_ptr, last_op, loc.clone(),
    )?;
    helpers::insert_op(ctx, shuffle, block_ptr, prepared_last_op);
    let result = shuffle.deref(ctx).get_result(0);
    Ok(Some(helpers::emit_prepared_result_and_goto(
        ctx, prepared_destination, result, target, block_ptr, shuffle,
        value_map, block_map, loc,
        "shuffle_xor_sync call without target block",
    )?))
}
```

该分支把用户的 MIR 操作数翻译为 pliron 值 —— 通常是来自每个操作数 alloca
栈槽的 `mir.load` 结果，或者字面量参数的 `mir.constant` —— 然后在插入 NVVM
操作之前准备好调用目标。结果随后通过那个准备好的目标写入，这样动态投影不会
在内联函数执行之后被重新求值。（它们还不是 SSA 值；`pliron::opts::mem2reg`
会在翻译完成后折叠这些 load/store 链。）对于目录内联函数，这些你都不用写：
`cuda-intrinsics-gen` 会从解析后的生成目录中派生出它。

### 第 4 阶段 —— 下降为 LLVM 方言

**文件：** `cuda-oxide/crates/mir-lower/src/convert/intrinsics/warp.rs`

这里就是第四个参数出现的地方。`dialect-nvvm` 操作携带三个操作数；而 butterfly
shuffle 的 LLVM 内联函数接受**四个**：

```text
User's shorthand: shuffle_xor(value, lane_mask)                     →  2 args
Intrinsic stub:   shuffle_xor_sync(mask, value, lane_mask)          →  3 args
                                   ^^^^
                                   u32::MAX from the Stage 1 wrapper
LLVM intrinsic:   shfl.sync.bfly.i32(mask, value, lane_mask, clamp) →  4 args
                                                             ^^^^^
                                                             always 31
```

转换器转发那三个操作数，只额外加上 clamp 常量：

```rust
pub(crate) fn convert_shuffle_i32(
    ctx: &mut Context,
    rewriter: &mut DialectConversionRewriter,
    op: Ptr<Operation>,
    _operands_info: &OperandsInfo,
    intrinsic_name: &str,
    clamp: i32,
) -> Result<()> {
    let i32_ty = IntegerType::get(ctx, 32, Signedness::Signless);

    let operands: Vec<_> = op.deref(ctx).operands().collect();
    if operands.len() != 3 {
        return pliron::input_err_noloc!(
            "Warp shuffle i32 requires 3 operands [mask, value, lane_or_delta]"
        );
    }
    let (mask, val, lane_or_delta) = (operands[0], operands[1], operands[2]);

    let clamp_val = create_i32_const(ctx, rewriter, clamp);

    let func_ty = llvm_types::FuncType::get(
        ctx,
        i32_ty.into(),
        vec![i32_ty.into(), i32_ty.into(), i32_ty.into(), i32_ty.into()],
        false,
    );

    let call_op = call_intrinsic(
        ctx, rewriter, op, intrinsic_name, func_ty,
        vec![mask, val, lane_or_delta, clamp_val],
    )?;
    rewriter.replace_operation(ctx, op, call_op);
    Ok(())
}
```

掩码在这里是普通操作数，而不是转换器制造的常量：第 1 阶段的包装器内嵌了
`u32::MAX`（全部 32 个 lane 参与），而带掩码的 `_sync` 形式让用户可以传入任意
掩码。clamp 值 `31` 由调用该转换器的生成 `MirToLlvmConversion` 实现按 shuffle
模式提供，意味着 shuffle 跨越完整 warp 宽度。它是指令模式的一个固定属性，把
它暴露给用户只会是噪音。

### 第 5 阶段 —— 导出（添加 convergent）

warp shuffle 是 **convergent** 的 —— LLVM 不得相对于控制流重排它们。导出步骤
检查 `is_convergent_intrinsic()`：

```rust
fn is_convergent_intrinsic(name: &str) -> bool {
    name == "llvm.nvvm.barrier0"
        || name.starts_with("llvm.nvvm.shfl")      // 洗牌
        || name.starts_with("llvm.nvvm.vote")       // 投票
        || name.starts_with("llvm.nvvm.mbarrier")   // 异步屏障
        || name.starts_with("llvm.nvvm.cp.async.bulk")
        // ...
}
```

如果你新增的内联函数是 convergent 的，就加在这里。如果你忘了，LLVM 可能会把它
提升出一个 `if` 块，你的 warp 级代码就会产生错误结果或死锁。不太好。

**最终输出：**

```llvm
declare i32 @llvm.nvvm.shfl.sync.bfly.i32(i32, i32, i32, i32)

%v8 = call i32 @llvm.nvvm.shfl.sync.bfly.i32(
    i32 -1, i32 %v3, i32 %v4, i32 31) #0

attributes #0 = { convergent }
```

经过 `llc` 之后：

```text
shfl.sync.bfly.b32  %r3, %r1, %r2, 31;
```

## 内联 PTX 路径

有些操作没有 LLVM 内联函数。对于这些，我们直接发出内联 PTX 汇编。辅助函数
`inline_asm_convergent()` 处理样板代码：

```rust
// wgmma fence：没有输入，没有输出，只有一个副作用
inline_asm_convergent(
    ctx, void_ty.into(), vec![],
    "wgmma.fence.sync.aligned;", ""
);

// mbarrier arrive：一个输入（指针），一个输出（令牌）
inline_asm_convergent(
    ctx, i64_ty.into(), vec![ptr_val],
    "mbarrier.arrive.shared.b64 $0, [$1];", "=l,r"
);
```

约束字符串遵循 LLVM 内联汇编语法：

| 约束       | 含义                                    |
| :--------- | :-------------------------------------- |
| `=l`       | 输出：64 位寄存器                       |
| `=r`       | 输出：32 位寄存器                       |
| `r`        | 输入：32 位寄存器                       |
| `l`        | 输入：64 位寄存器                       |
| （空）     | 无输入或输出（仅有副作用）              |

内联汇编上的 `sideeffect convergent` 标记告诉 LLVM 别动它 —— 不要移动它，
不要删除它，不要复制它。

## 端到端：完整旅程

以下是 `threadIdx_x` 自上而下经过的每一种表示：

```text
Rust:         thread::threadIdx_x()
MIR:          _3 = threadIdx_x() -> bb1
Pliron MIR:   %v = nvvm.read_ptx_sreg_tid_x : i32
Pliron LLVM:  %v = call i32 @llvm_nvvm_read_ptx_sreg_tid_x()
LLVM IR:      %v5 = call i32 @llvm.nvvm.read.ptx.sreg.tid.x()
PTX:          mov.u32 %r1, %tid.x;
```

以及 `shuffle_xor_sync`，即 `shuffle_xor` 简写背后的桩：

```text
Rust:         warp::shuffle_xor_sync(u32::MAX, val, lane)
MIR:          _5 = shuffle_xor_sync(const u32::MAX, _3, _4) -> bb2
Pliron MIR:   %v = nvvm.shfl_sync_bfly_i32 %mask, %val, %lane : u32
Pliron LLVM:  %v = call i32 @llvm_nvvm_shfl_sync_bfly_i32(i32 -1, %val, %lane, i32 31)
LLVM IR:      %v8 = call i32 @llvm.nvvm.shfl.sync.bfly.i32(i32 -1, %v3, %v4, i32 31) #0
PTX:          shfl.sync.bfly.b32 %r3, %r1, %r2, 31;
```

六种表示。一次 Rust 函数调用变成一条 PTX 指令。中间步骤的存在，是为了让每一次
变换都保持小、可校验、可独立测试。

## 速查清单

对于一个手写内联函数（即 `intrinsics/catalog.json` 无法描述的那个），你需要
按顺序触碰的每个文件：

1. **`cuda-device/src/<module>.rs`** —— 带 `#[inline(never)]` 和
   `unreachable!()` 函数体的 `pub fn`。这是面向用户的 API。

2. **`dialect-nvvm/src/ops/<module>.rs`** —— `#[pliron_op(name = "nvvm.<name>", ...)]`
   结构体、`Verify` 实现（检查操作数/结果数量）、`register()` 调用。

3. **`mir-importer/src/translator/terminator/mod.rs`** ——
   `try_dispatch_intrinsic()` 中的 `match` 分支，仿照手写的 `typed_swap` 分支。
   零操作数内联函数属于目录的地盘：生成的调度器通过
   `helpers::emit_generated_nvvm_intrinsic()` 发出它们，后者串接 MIR 函数体，
   以便在生成的操作之前准备好目标，同时还盖上手写分支本需自己盖的 ABI 标记。

4. **`mir-lower/src/convert/interface_impls.rs`** —— 为新操作实现
   `MirToLlvmConversion`，分发到转换器函数。

5. **`mir-lower/src/convert/intrinsics/<module>.rs`** —— 转换逻辑。对 LLVM
   内联函数使用 `call_intrinsic()`，或者对内联 PTX 使用
   `inline_asm_convergent()`。

6. **`llvm-export/src/export/`** —— *仅当是 convergent 时*：加入
   `is_convergent_intrinsic()`。

对于目录内联函数，第 2 到第 4 步不由你编写。扩展相应的
`intrinsics/overlay/*.toml` 族，在 `intrinsics/abi-v1.toml` 中追加 ABI 条目，
只在路径要求时添加证据，然后重新生成。`intrinsics/catalog.json` 是生成的，
不得手工编辑。完整工作流见
[目录生成的内联函数](catalog-generated-intrinsics.md)。

## 并排比较

| 阶段         | `threadIdx_x`（简单）          | `shuffle_xor_sync`（复杂）          |
| :----------- | :---------------------------- | :--------------------------------- |
| cuda-device  | `fn() -> u32`                 | `fn(u32, u32, u32) -> u32`         |
| dialect-nvvm | 0 个操作数，1 个结果           | 3 个操作数，1 个结果                |
| mir-importer | 生成的分支，通用辅助函数        | 生成的分支，操作数翻译              |
| mir-lower    | `call @intrinsic()`           | `call @intrinsic(4 args)`          |
| Convergent？ | 否                            | 是（`#0`）                          |
| PTX          | `mov.u32 %r1, %tid.x`         | `shfl.sync.bfly.b32 ...`           |

---

这就是端到端的手写流水线。对于占多数的目录生成路径，请使用
[目录生成的内联函数](catalog-generated-intrinsics.md) 中的 overlay、ABI、证据、
生成和验证工作流。
